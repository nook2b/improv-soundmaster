# AI-звукарь для импров-шоу — план (ревизия 3)

> Исправленная версия исходного плана. Что изменено и почему — в разделе 0 (ревизия 2) и 0.1 (ревизия 3). Предложения по развитию — в разделе 19.

## Цель проекта

Создать систему, которая во время импровизационного шоу в реальном времени:

- видит происходящее на сцене через камеру;
- слышит реплики и звуки со сцены;
- понимает контекст сцены;
- ставит подходящие звуковые эффекты (сначала — предлагает, затем — автоматически только для проверенных случаев);
- при необходимости запускает музыку или атмосферу;
- предлагает момент для отбивки;
- в дальнейшем может управлять OBS, светом и другими элементами шоу.

Ключевой принцип: нейросеть не должна «пытаться быть смешной». Она работает как технический участник шоу и вмешивается только тогда, когда действие уже совершено актёрами и однозначно считывается.

Второй принцип: **живой техник всегда главнее AI**. Ручной пульт работает всегда — даже если упал интернет, API или модель.

## 1. Общая архитектура

```
Камера ──────────────┐
                     ├──> Multimodal Live AI ──> Cue Controller ──> Audio Engine ──> Микшер ──> Зал
Микрофоны ─> Микшер ─┤        (что)             (можно ли)          (когда/как)
   (aux без SFX)     │                              ▲
                     └──> Локальный быстрый слой ───┘   (fire-триггеры: ключевые слова, транзиенты)
                                                    ▲
                                       Пульт оператора (всегда главнее)
```

Части системы:

1. **Видео** — общий план сцены; кадры уходят модели ~1 раз в секунду (частота и разрешение подбираются на этапе 1).
2. **Аудио** — отдельная aux-шина микшера только с микрофонами актёров; передаётся модели в реальном времени. Электрически звуки системы в неё не попадают, но акустически колонки всё равно проникают в микрофоны — поэтому модель дополнительно получает текстовые события о том, что сейчас играет, а быстрый слой глушит транзиент-детектор на время собственных звуков.
3. **AI-модель** — понимает реплики и происходящее, выбирает действие, **не генерирует звук и не говорит** (вывод модели — только текст/function calls), вызывает только разрешённые функции.
4. **Локальный быстрый слой** (с этапа 3) — локальное распознавание ключевых слов и детектор резких звуков/хлопков. Сам эффекты не выбирает: срабатывает для уже «взведённых» cue и может взвести cue по ключевому слову-подводке, явно прописанному в реестре.
5. **Cue Controller** — проверяет команды, применяет ограничения, ведёт лог.
6. **Audio Engine** — проигрывает предзагруженные звуки по каналам с ducking.
7. **Пульт оператора** — ручной запуск любого звука, подтверждение предложений, kill switch, кнопка «Новая сцена».

## 2. Почему модель не управляет звуком напрямую

Модель выдаёт только структурированные команды; локальная программа решает, выполнять ли их.

```
play_sfx(cue, confidence, reason)                 # cue — enum из реестра
arm_sfx(cue, trigger, timeout, confidence, reason) # взвести эффект, сработает по триггеру
play_music(cue, confidence, reason)
play_ambience(cue, confidence, reason)
stop_music(reason)                                 # длительность фейда берётся из реестра
stop_ambience(reason)
suggest_scene_end(confidence, reason)             # только предложение, отбивку запускает человек
```

- `cue` — строго `enum` в схеме функции: модель не может вызвать несуществующий звук.
- `trigger` — `enum`: `transient | keyword | operator`; допустимые для cue триггеры и ключевые слова заданы в реестре.
- `timeout` — секунды, ограничен сверху значением из реестра.
- `reason` — короткое (до ~10 слов) описание увиденного/услышанного, обязательно (нужно для лога и разметки). Стоит **последним** аргументом: контроллер может начать обработку, как только в потоке аргументов пришли `cue` и `confidence`, не дожидаясь генерации `reason`.
- `confidence` — `low | medium | high`; используется как слабый сигнал.

Это защищает от случайных повторов, нескольких SFX одновременно, слишком частых вмешательств, ложных отбивок и задержек из-за генерации звука.

## 3. MVP

### Входные данные

- одна камера (общий план, хорошо освещённая сцена);
- одна aux-шина со сцены без звуков самой системы;
- 15–20 заранее подготовленных звуков в WAV.

### Базовая библиотека

**SFX (канал `sfx`):** затвор фотоаппарата, дверной звонок, звонок телефона, удар, падение, автомобиль, сирена, касса, магический эффект.

**Громкие SFX (режим `confirm` по умолчанию):** выстрел, взрыв. Ложное срабатывание громкого эффекта — самая дорогая ошибка: пугает зал и навязывает актёрам действие.

**Музыка (канал `music`):** романтическая, тревожная.

**Атмосфера (канал `ambience`):** хоррор, офис, ресторан, дождь, улица.

**Отбивки (канал `sting`):** финальная отбивка.

Аплодисменты из MVP убраны: AI, «аплодирующий» сам себе или актёрам, воспринимается как закадровый смех и почти всегда лишний.

Музыка — только royalty-free или с лицензией на публичное исполнение.

### Что должна уметь модель

Актёр говорит:

> Смотрите сюда. Сейчас вылетит птичка.

…и изображает фотографа. Реплика звучит **до** действия — значит, модель может заранее взвести эффект:

```
arm_sfx(cue="camera_shutter", trigger="transient", timeout=3, confidence="high",
        reason="актёр готовится фотографировать")
```

Затвор срабатывает в момент «щелчка» (звук актёра, хлопок, ключевое слово «чик») или по кнопке оператора; если за таймаут ничего не произошло — cue снимается.

Ограничение: `arm_sfx` приходит через 1–3 с после реплики. Если щелчок звучит сразу за «птичкой», AI не успеет. Поэтому слово «птичка» само по себе прописано в реестре как локальная подводка: быстрый слой взводит затвор сразу, а AI служит для случаев, когда подводка видна по контексту заранее (актёр долго выстраивает кадр).

## 4. Cue Controller

Обязательная прослойка между AI и звуком. Единый реестр cue:

```yaml
channels:
  sfx:      { max_simultaneous: 1 }
  music:    { max_simultaneous: 1, duck_under: [sfx, sting], duck_db: -8 }
  ambience: { max_simultaneous: 1, duck_under: [sfx, sting], duck_db: -6 }
  sting:    { max_simultaneous: 1, stops: [music, ambience] }

global:
  min_gap_between_different_ai_cues: 3.0   # секунд между РАЗНЫМИ AI-эффектами;
                                           # повторы одного cue — только его cooldown/max_repeat
  max_ai_cues_per_minute: 6                # серия повторов одного cue считается за один
  min_confidence_auto: high
  dedupe_window: 3.0                       # после fire взведённого cue play того же cue игнорируется
  late_drop:                               # отсчёт от t_commit хода, на котором принято решение
    reactive: 3.0
    instant: 0.0                           # instant прямым вызовом в auto не играется вообще
  # Все лимиты применяются только к автоматическим решениям AI.
  # Ручной запуск и подтверждение оператором их обходят (лимитер громкости — нет).

cues:
  camera_shutter:
    file: sfx/camera_shutter.wav
    channel: sfx
    class: instant        # instant | reactive
    mode: auto            # auto | confirm | off
    cooldown: 1.5
    max_repeat: { count: 5, window: 30 }   # не больше 5 раз за 30 секунд
    arm:
      triggers: [transient, keyword, operator]
      fire_keywords: ["чик", "щёлк"]
      arm_keywords: ["птичка", "улыбочку"]  # локальный быстрый слой взводит сам
      max_timeout: 5

  doorbell:
    file: sfx/doorbell.wav
    channel: sfx
    class: reactive
    mode: auto
    cooldown: 5

  gunshot:
    file: sfx/gunshot.wav
    channel: sfx
    class: instant
    mode: confirm         # громкий — только через оператора
    cooldown: 10

  romantic:
    file: music/romantic.wav
    channel: music
    mode: confirm
    do_not_restart_if_playing: true
    fade_in: 2.0
    fade_out: 3.0

  scene_end:
    file: sting/scene_end.wav
    channel: sting
    mode: confirm         # AI только предлагает, запускает оператор
    cooldown: 30
```

Контроллер умеет:

- cooldown на cue и глобальный лимит частоты;
- ограничение повторов в скользящем окне;
- каналы, приоритеты, ducking, взаимоисключения;
- режим cue: `auto` / `confirm` / `off` — переключается на лету;
- запрещать прямой `play_sfx` для `instant`-cue в режиме `auto` (только arm → fire или оператор);
- дедуплицировать пару «сработавший arm» + запоздалый `play_sfx` того же cue;
- снимать «взведённые» cue по таймауту и при смене сцены;
- игнорировать команды, пришедшие с опозданием: порог по классу cue, отсчёт от `t_commit` — момента, когда клиент закрыл ход (realtime-API не сообщает, на каком кадре основано решение, поэтому опорная точка — граница хода);
- глушить транзиент-детектор на время звучания собственных эффектов + ~300 мс хвоста;
- отправлять модели текстовые события о состоянии: что играет, что взведено, подсказка сцены;
- логировать каждое решение, включая причину блокировки;
- kill switch: одной клавишей отключить всю автоматику, снять все взведённые cue и (вторым нажатием или отдельной клавишей) заглушить звуки AI; ручной пульт продолжает работать.

## 5. Системная инструкция для AI

```
Ты технический звукорежиссёр импровизационного шоу. Ты не говоришь и не
комментируешь — только вызываешь функции или ничего не делаешь.

Ставь эффект, только когда действие или ситуация однозначно считываются
из происходящего на сцене. Эффект усиливает уже совершённое актёрами
действие и не придумывает новое за них: каждый звук в импрове — это
предложение, которое актёры будут вынуждены принять.

Если не уверен — ничего не делай. Бездействие — нормальный и частый ответ:
тебя спрашивают каждую секунду, и почти всегда правильный ответ — пустой.

Мгновенные эффекты (затвор, удар, падение) не ставь по факту — ты
опоздаешь. Взводи их через arm_sfx, когда видишь подготовку к действию.
Если подготовки не было — пропусти.

Не ставь эффект в ответ на смех или реакцию зала. Смех учитывай только
при решении о конце сцены (см. инструкцию к suggest_scene_end).

Не реагируй на:
- упоминания без действия («надо бы позвонить маме» — это не звонок);
- отрицание и гипотетику («хорошо, что не было взрыва»);
- звуки, музыку и атмосферу, которые запущены системой. Ты получаешь
  сообщения вида [СИСТЕМА: играет doorbell] — если звук в аудио совпадает
  с ними, это не событие сцены.

Сообщение [НОВАЯ СЦЕНА: ...] содержит подсказку зала — используй её как
контекст (место, жанр), но не ставь эффект только из-за неё.

Если актёр сам озвучивает эффект голосом («дзынь-дзынь!») — обычно не
дублируй его.

Не ставь эффекты часто. Не пытайся шутить поверх актёров.

В поле reason коротко (до 10 слов) опиши, что именно ты увидел или услышал.
```

## 6. Работа с отбивками

Отбивка сложнее обычного SFX. Модель должна оценить:

- был ли сильный панч;
- закончилась ли смысловая линия;
- есть ли естественная пауза;
- не разрушит ли продолжение уже возникший момент.

Функция: `suggest_scene_end(reason, confidence)`.

AI не заканчивает сцену сам:

```
AI считает, что сцену пора закончить
        ↓
загорается индикатор у техника (и, по желанию, у ведущего)
        ↓
техник подтверждает (отдельная клавиша/кнопка отбивки) или игнорирует
        ↓
звучит отбивка
```

Подсказка гаснет сама через несколько секунд, если её не подтвердили, — чтобы техник не нажал на «протухшее» предложение.

У каждого типа подсказки — своя клавиша. Одна общая клавиша «подтвердить» (например, Space) опасна: если одновременно висят предложение SFX и предложение отбивки, непонятно, что именно подтверждается. Space в браузере к тому же прокручивает страницу и нажимает кнопку в фокусе.

Переход к автоматической отбивке — только после того, как по статистике нескольких шоу доля «perfect» стабильно высокая, а «too early» близка к нулю. Скорее всего, для отбивок режим `confirm` останется навсегда: это художественное решение команды.

## 7. Инструкция для определения конца сцены

```
Предлагай завершить сцену в одном из двух случаев.

Случай А — выполнены ВСЕ три условия:
1. произошёл сильный комедийный панч;
2. после него появилась естественная пауза (сообщение [ЗАЛ: смех]
   и актёры не продолжают линию);
3. дальнейшее развитие скорее ослабит момент.

Случай Б — история очевидно получила завершение.

Не предлагай завершение:
- просто из-за молчания;
- из-за случайной паузы;
- потому что сцена долго идёт;
- если актёры продолжают активно развивать новую идею.
```

Смех зала здесь полезен как сигнал, но модель его не слышит (aux только с актёрами, а проникающий в микрофоны смех ненадёжен). Поэтому уровень с зального микрофона обрабатывается локально (порог + длительность), и модель получает короткие текстовые события `[ЗАЛ: смех]` / `[ЗАЛ: тишина]`. То же событие показывается технику рядом с подсказкой.

## 8. Технический стек

### Компьютер

Windows-ноутбук, проводной интернет (Wi-Fi площадки ненадёжен) + резервный 4G/5G-модем.

### Программа

Python (asyncio): клиент realtime-API, контроллер, веб-интерфейс оператора на localhost. Аудиодвижок и быстрый слой — в отдельном потоке аудио-callback (например, `sounddevice`) или отдельном процессе: подвисание event loop на обработке кадра или JSON не должно задерживать звук и ручной пульт.

Ручной пульт — физический: MIDI-контроллер, Stream Deck или педаль. Браузерные горячие клавиши работают только при фокусе на вкладке.

### Видео

USB-камера или камера через карту захвата; позже — виртуальная камера OBS. Учесть сценический свет: веб-камеры плохо работают с контрастными пятнами прожекторов — нужна ручная экспозиция.

### Аудио

```
микрофоны актёров
   ↓
микшер
   ├──> main ──> колонки (сюда же — выход ноутбука)
   └──> aux (pre-fader, только микрофоны актёров) ──> аудиоинтерфейс ──> AI

зальный микрофон ──> только индикатор громкости зала (для отбивок)
```

Выход ноутбука идёт в микшер **отдельным каналом**, который не попадает в aux для AI.

Акустическое проникновение колонок в микрофоны актёров этим не устраняется. На саундчеке система проигрывает тестовые звуки в зал и измеряет их уровень в aux; если он высокий — подбирать направленность/положение микрофонов, а при необходимости вычитать собственный выход (эхоподавление с опорным сигналом выхода ноутбука).

### AI

Кандидаты: Gemini Live API, OpenAI Realtime API. Что проверить на этапе 1 для каждого:

- приём аудио и изображений в одной сессии;
- function calling во время стрима и задержка до вызова функции;
- режим «без голосового ответа» (только текст/вызовы функций);
- ручное управление ходами при непрерывной речи на сцене;
- максимальная длительность сессии, переподключение, восстановление контекста;
- стоимость часа работы (аудио + кадры) **именно в режиме ручных ходов**: запрос ответа каждые 1–1.5 с — это тысячи ответов в час, и каждый обрабатывает накопленный контекст;
- рост контекста и его ограничение (сжатие, обрезка старого аудио/кадров);
- доступность API из страны площадки и способ оплаты.

### Проигрывание звука

- только WAV, предзагрузка в память при старте;
- вывод через ASIO или WASAPI; exclusive-режим захватывает устройство целиком, поэтому выход AI — отдельное устройство/пара каналов интерфейса, не занятые другими программами;
- никакой генерации SFX нейросетью во время шоу.

## 10. Логирование

Лог — JSONL, одна запись на решение:

```json
{
  "show_id": "2026-10-10-evening",
  "session_id": "s3",
  "scene_id": 4,
  "versions": { "prompt": "p12", "model": "<id модели>", "registry": "r5" },
  "source": "ai",
  "t_commit": 812.6,
  "t_tool_call": 813.9,
  "t_armed": 813.9,
  "t_fired": 814.4,
  "fired_by": "transient",
  "t_played": 814.42,
  "cue": "camera_shutter",
  "call": "arm_sfx",
  "reason": "актёр готовится фотографировать",
  "confidence": "high",
  "result": "fired",
  "blocked_by": null
}
```

- Все `t_*` — секунды по одним монотонным часам системы от старта записи; эти же часы используются в записи входного потока.
- `t_commit` — момент, когда клиент закрыл ход и запросил ответ. Точнее определить, на каком кадре/фрагменте основано решение, нельзя.
- `source`: `ai | fast_layer | operator` — ручные запуски оператора логируются тоже (это эталон и материал для поиска пропусков).
- `result`: `played | suggested | confirmed | rejected | armed | fired | expired | blocked | late_dropped | deduped`.
- `versions` обязательны: без них результаты replay разных версий не сравнить.
- Разметка (`operator_label`) хранится отдельным файлом, а не в логе решений, — см. раздел 11.

Таймстемпы позволяют разложить задержку по звеньям: ход → ответ модели → (взведение → срабатывание) → воспроизведение.

**Запись прогона.** Система сама пишет ровно то, что ушло модели (аудио aux, отправленные кадры, границы ходов, текстовые события), плюс зальный уровень и выход main — всё на тех же часах. Отдельная видеозапись (OBS) удобна для разметки, но для replay не годится: она не совпадает с тем, что видела модель.

## 11. Feedback loop и replay-стенд

### Разметка: эталонная дорожка, а не оценки решений

Если размечать решения конкретной версии («правильно / слишком рано»), разметка не переносится на следующую версию: она примет другие решения. Поэтому каждая запись размечается один раз **эталонной дорожкой событий** (по видео, на таймлайне):

```yaml
- { t: 812.9, cue: camera_shutter, window: [812.7, 813.2], kind: required }   # момент щелчка
- { t: 640.0, cue: doorbell,       window: [639.5, 642.0], kind: acceptable } # можно, но не обязательно
- { t: 901.3, cue: gunshot,                                kind: forbidden }  # «хорошо, что не выстрелил»
- { t: 1210.0, cue: scene_end,     window: [1208, 1215],   kind: acceptable }
```

- `required` — эффект должен прозвучать в окне (иначе пропуск);
- `acceptable` — допустим, но не обязателен;
- `forbidden` — ловушка: типичное ложное срабатывание (упоминание без действия, отрицание);
- всё, что сыграно вне окон, — ложное срабатывание; сыгранное в окне `required`, но позже его конца, — «поздно».

Решения любой версии сопоставляются с дорожкой **автоматически** → точность, полнота, задержка, ложные срабатывания. Ручная оценка нужна только для новых спорных случаев, которые затем добавляются в дорожку.

Как использовать разметку:

- **Не копировать сырые примеры в промпт** — он раздувается, это увеличивает задержку и стоимость, а текстовое описание не передаёт видео. Из ошибок выводятся **короткие правила** («звук телефона только при жесте трубки у уха»), плюс несколько коротких текстовых примеров «ситуация → действие / бездействие».
- Ошибки по конкретному cue в первую очередь чинятся режимом и лимитами контроллера, а не промптом.

**Replay-стенд:** записанный входной поток (раздел 10) подаётся в систему как живой, с теми же границами ходов. Любое изменение промпта, модели или порогов прогоняется на всех записях, метрики сравниваются с предыдущей версией. Это главный инструмент разработки — без него каждое улучшение требует живых актёров.

Особенности:

- ответы модели недетерминированы — каждую запись прогонять 2–3 раза и сравнивать средние и разброс, а не один прогон;
- realtime-API работает в реальном времени: час записей = час прогона и стоимость часа. Держать короткий «регрессионный набор» из 15–20 минут самых показательных фрагментов, полный набор — перед изменением режимов на шоу;
- контроллер и быстрый слой тестируются на replay без модели (по записанным ответам) — быстро и бесплатно.

## 12. Этапы разработки

### Этап 1 — Proof of Concept

Цель: проверить, что AI понимает сцену, и измерить реальную задержку.

- камера + aux-аудио + realtime-API;
- предложения выводятся текстом с таймстемпами, без воспроизведения;
- запись входного потока для replay (раздел 10) — с первого дня;
- сравнение 2 провайдеров по чек-листу из раздела 8;
- проверка: отвечает ли модель вовремя при непрерывной речи на сцене;
- **базовая линия без LLM**: локальное распознавание речи + словарь ключевых слов → те же cue. Если она даёт сравнимую полноту по части cue, для них LLM не нужна.

### Этап 2 — MVP Soundboard

- 15–20 звуков в WAV, предзагрузка: SFX + 2 музыкальные подложки + 2–3 атмосферы;
- function calling с enum cue;
- Cue Controller: cooldown, лимиты, каналы, дедупликация, late-drop, лог;
- **ручной пульт, kill switch, кнопка «Новая сцена»** (сброс контекста, ввод подсказки зала);
- все cue в режиме `confirm`; в `auto` по одному переводятся только **реактивные** SFX после проверки на replay. Мгновенные SFX в `auto` — только с этапа 3 (через arm → fire);
- музыка и атмосфера — только `confirm`/вручную, фейды фиксированные из реестра, без автоматической громкости.

Цель: полноценный прогон, на котором техник не теряет контроль.

### Этап 3 — Human-in-the-loop + быстрый слой

Интерфейс техника:

```
[ CAMERA SHUTTER ]  high   "изображает фотографа"   [PLAY]  (гаснет через 4 с)
[ SCENE END ]       medium "панч + смех зала"        [PLAY]
```

- `arm_sfx` + локальные fire-триггеры (ключевые слова, транзиенты) с гейтом на время собственных звуков;
- локальное взведение по словам-подводкам из реестра;
- взведённые cue видны технику (можно снять или выстрелить вручную);
- очевидные SFX — `auto`, громкие и отбивки — `confirm`.

### Этап 4 — AI-звукарь

- автоматический выбор музыкальных подложек и ambience (`auto` для проверенных);
- адаптивные fade in / fade out, ducking;
- автоматическая громкость относительно уровня сцены;
- автоопределение начала новой сцены (как подсказка оператору).

### Этап 5 — AI-техник

OBS, свет (DMX — только через предустановленные сцены, никаких «сырых» каналов от модели), проектор, титры. (Запись шоу ведётся с этапа 1 и от AI не зависит.)

## 13. Главный технический риск — задержка

Для комедии критично время. Реалистичная картина при прямом вызове:

```
0.0 с   — действие актёра
0–1.5   — ожидание конца хода (ручные ходы каждые 1–1.5 с; кадр 1 fps укладывается сюда же)
0.1–0.3 — сеть до API и обратно
0.5–1.5 — модель формирует вызов функции (cue и confidence — первыми аргументами)
~0.05   — контроллер + запуск предзагруженного WAV
───────
итого ~0.7–3.3 с, типично 1.5–2.5 с
```

Отсюда порог late-drop для реактивных cue — около 3 с от `t_commit` (раздел 4): меньший порог отбрасывал бы заметную долю нормальных ответов.

Поэтому эффекты делятся на два класса:

1. **Реактивные** (атмосфера, музыка, звонок в дверь «в ответ» на «кто-то пришёл») — допускают 1–2 с, ставятся прямым вызовом.
2. **Мгновенные** (затвор, удар, падение) — задержка больше ~0.3 с убивает шутку. Схема **arm → fire**: модель по контексту заранее «взводит» cue (или его взводит быстрый слой по слову-подводке), а срабатывает он по быстрому локальному сигналу (хлопок/транзиент, ключевое слово, кнопка/педаль оператора). Если взведения не было — для мгновенных эффектов лучше пропустить, чем опоздать.

Задержка самих fire-триггеров разная: транзиент — десятки миллисекунд; ключевое слово — только после того, как слово прозвучало целиком, плюс 0.2–0.5 с на распознавание.

Метрики, которые измеряются отдельно (из таймстемпов раздела 10):

- задержка захвата аудио и видео;
- сеть до API;
- время от `t_commit` до function call;
- время от команды до звука в колонках;
- доля команд, отброшенных как опоздавшие;
- доля мгновенных событий эталонной дорожки, для которых cue был взведён **до** момента действия (а не после).

---

## 14. Принцип: звук локальный, момент — локальный

AI определяет **ЧТО** уместно сейчас.
Локальная система определяет, **МОЖНО ли** (контроллер) и **КОГДА ТОЧНО** (fire-триггер или оператор) это сыграть.

Звуковые файлы заранее загружены в память — эффект запускается за миллисекунды после разрешения.

## 16. Первый реальный эксперимент

Нужно:

- ноутбук, камера, aux со сцены **без канала живого техника**;
- 15–20 звуков;
- Python;
- Gemini Live и/или OpenAI Realtime;
- запись входного потока + видео с таймкодом (раздел 10).

**Важно: AI не должен слышать эффекты живого техника.** Иначе модель «распознаёт» звонок, который техник уже поставил, и метрики завышаются. Вариант «один микрофон в зале» для этого эксперимента не подходит: он слышит колонки. Если без него не обойтись — играть без живого техника, а эталон собирать только разметкой записи.

Тест:

1. сыграть 2–3 сессии по 10–15 минут импровизации;
2. не сообщать AI заранее, какие события произойдут;
3. живой техник параллельно работает как обычно. Чтобы его действия стали эталоном, он играет через ручной пульт системы (тогда они логируются с `source: operator`) или отмечает каждое событие кнопкой. Его эффекты попадают в зал, но не в aux для AI;
4. AI работает в режиме «только предлагать» (звук не идёт в зал);
5. после прогона построить эталонную дорожку событий (раздел 11), используя действия техника как черновик;
6. посчитать метрики раздела 17; предложения AI, пришедшие после звука техника по тому же событию, проверить на утечку;
7. сохранить записи для replay-стенда.

Это даёт 30–45 минут материала — достаточно, чтобы выбрать провайдера и найти грубые ошибки, но мало для метрик «за час» и «за шоу». Решения о переводе cue в `auto` принимаются после ≥ 3–4 часов размеченных записей.

## 17. Критерии успешного MVP

Ориентировочные пороги (уточнить после первого эксперимента):

Все метрики считаются автоматически по эталонной дорожке (раздел 11); «очевидные» события — это события `required`.

| Метрика | Цель MVP |
|---|---|
| Точность (доля попавших в окна `required`/`acceptable` среди сыгранных/предложенных) | ≥ 80 % |
| Полнота по событиям `required` | ≥ 60 % |
| Срабатывания на ловушки `forbidden` | 0 для громких cue, ≤ 10 % для остальных |
| Медианная задержка реактивных эффектов (от действия до звука) | ≤ 2 с |
| Задержка arm → fire, триггер-транзиент | ≤ 0.1 с |
| Задержка arm → fire, триггер-слово (от конца слова) | ≤ 0.5 с |
| Доля мгновенных событий, взведённых до действия | измерить на этапе 1, цель — по результатам |
| Ложные громкие эффекты | 0 за шоу |
| Ложные AI-эффекты в зал | ≤ 2 за час |
| Ложные подсказки отбивки | ≤ 1 за 3 сцены |
| Вмешательства оператора (kill/отмена) | ≤ 3 за час |
| Обрывы сессии без автоматического восстановления | 0 |

Медианная цель для реактивных эффектов поднята до 2 с — она должна быть совместима с бюджетом раздела 13 (типично 1.5–2.5 с). Если на этапе 1 окажется, что ≤ 1.5 с достижимо, порог ужесточить.

И качественные критерии: AI умеет ничего не делать в неоднозначной ситуации, система не отвлекает актёров и зрителей.

Главная задача первого прототипа — не автономность, а проверка, может ли AI быть аккуратным техническим партнёром импров-команды.

## 18. Риски и эксплуатация

- **Сеть.** Проводное подключение + резервный модем. При потере связи система сама переходит в ручной режим, на пульте — заметный индикатор.
- **Отказ API.** Ручной пульт не зависит от AI. Шоу никогда не должно зависеть от облака.
- **Стоимость.** Непрерывный поток аудио + кадров тарифицируется по токенам, а ручные ходы каждые 1–1.5 с многократно обрабатывают накопленный контекст. Посчитать стоимость часа на этапе 1 в реальном режиме ходов, выбрать частоту кадров/разрешение, ограничить длину контекста. Жёсткий лимит расходов на шоу на стороне клиента.
- **Доступность провайдера.** Проверить, что API официально доступен в стране площадки и есть способ оплаты; иметь второго провайдера как запасной вариант.
- **Зависание модели.** Если от модели нет событий дольше N секунд или сессия переподключается — индикатор на пульте; взведённые cue снимаются.
- **Приватность.** Видео зала и сцены уходит в облако: камера направлена только на сцену, зрителей предупредить (афиша/объявление), проверить политику провайдера по хранению данных.
- **Лицензии.** Музыка и SFX — с правом публичного исполнения.
- **Громкость.** Лимитер на выходе ноутбука; громкие cue — только `confirm`.
- **Актёры.** Команда заранее знает, что в зале AI-техник и как он реагирует (например, «птичка» взводит затвор), — это часть договорённостей, как с живым техником.

## 19. Предложения по улучшению

Не ошибки, а то, что заметно повысит шансы проекта.

1. **Базовая линия без LLM (этап 1).** Локальное распознавание речи + словарь «фраза → cue». Многие эффекты (звонок, «птичка», «сирена») выводятся из слов. Если базовая линия даёт сравнимую полноту, LLM нужна только для визуальных и контекстных случаев, а система дешевле, быстрее и работает без интернета.
2. **Модель знает состояние системы.** Контроллер шлёт короткие текстовые события: `[СИСТЕМА: играет romantic]`, `[ВЗВЕДЕНО: camera_shutter]`, `[НОВАЯ СЦЕНА: ресторан, нуар]`, `[ЗАЛ: смех]`. Это снижает повторные `play_music` того же трека, реакцию на собственные звуки и делает подсказку зала полезной.
3. **Потоковая обработка вызова функции.** `cue` и `confidence` идут первыми аргументами, `reason` — последним и коротким; контроллер готовит воспроизведение по частично полученным аргументам. Экономия — сотни миллисекунд на каждый реактивный эффект.
4. **Теневой режим на реальных шоу.** Между этапами 2 и 3 — несколько настоящих шоу, где система только показывает предложения на отдельном экране техника и пишет данные. Это самый дешёвый способ набрать часы размеченного материала в реальных условиях (свет, зал, усталость актёров).
5. **Саундчек-самотест перед шоу.** Автоматический чек-лист: связь с API, задержка, проигрывание тестовых звуков в зал и замер их уровня в aux (проникновение), работа транзиент-детектора, ручной пульт, запись. Красный пункт — шоу идёт в ручном режиме.
6. **Версионирование всего, что влияет на решения.** Промпт, реестр cue, пороги быстрого слоя — в git; версии пишутся в каждую запись лога. Replay-отчёт сравнивает версии бок о бок.
7. **Эталонная дорожка как общий актив команды.** Размеченные записи — главная ценность проекта, независимая от провайдера. С ними можно сменить модель за день, а не за месяц живых прогонов.
8. **Отдельный экран для актёров/ведущего (по желанию).** Маленький индикатор «взведено: затвор» помогает актёрам подыгрывать системе так же, как они подыгрывают живому технику, — и превращает задержку из проблемы в договорённость.
